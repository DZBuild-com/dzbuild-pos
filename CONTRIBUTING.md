# Contributing to DZBuild POS

DZBuild POS is maintained by the DZBuild team. Shops use it to sell and to keep their books, so a
change has to be correct before it is merged.

You can help by fixing a bug, building a feature from an issue, improving an Arabic, French or
English wording, testing a printer or a scale, improving the docs, or answering questions in
[Discussions](https://github.com/DZBuild-com/dzbuild-pos/discussions).

For a large change, open an issue or a discussion first so the approach can be agreed before you
write code. Security problems never go in a public issue: see [SECURITY.md](SECURITY.md).

## Set up

You need Windows 10 1809+ or 11, Rust stable (installed by [`rust-toolchain.toml`](rust-toolchain.toml)),
Visual Studio Build Tools 2022 with "Desktop development with C++", Node.js 24, pnpm (`corepack
enable`) and the WebView2 runtime.

```powershell
git clone https://github.com/<you>/dzbuild-pos.git
cd dzbuild-pos
pnpm install
pnpm tauri dev
```

Development data lives in `%APPDATA%\dev.dzbuild.pos\`. Rename that folder to start from a fresh
setup wizard.

## Test

| Command | What it checks |
| --- | --- |
| `pnpm check` | Everything CI checks, in CI order: ESLint, TypeScript, Vitest, tooling tests, i18n parity, Prettier and rustfmt, Clippy, Rust tests. Run it before you push. |
| `cargo test --workspace` | The Rust tests alone (domain, database, documents, hardware, LAN). |
| `pnpm test` | The interface tests (Vitest with mocked commands). |
| `pnpm e2e` | End-to-end flows in a browser (Playwright; run `pnpm exec playwright install chromium` once). |
| `pnpm i18n` | Every key exists in Arabic, French and English. |

Money, tax, stock and kridi logic is written test first: add a failing test, then make it pass, and
show the test output in your pull request.

## Code style

- Formatting is automatic: `pnpm format` (Prettier and rustfmt). Lint must be clean:
  `pnpm lint` (zero warnings) and `cargo clippy --workspace --all-targets -- -D warnings`.
- **Money is integer centimes**: `i64` in Rust, an integer `number` in TypeScript. Never a float for
  an amount. Tax and stamp rounding live in `pos-core::tax` only.
- **No `unwrap()` or `expect()` in command paths**: return `Result<T, AppError>`.
- **No SQL in the interface**: the UI calls typed commands. `src/bindings.ts` is generated by
  tauri-specta; after changing a command, regenerate it with
  `cargo test -p dzbuild-pos write_bindings -- --ignored`.
- **Logical CSS only**: `ms-`, `pe-`, `start`, `end`; never left or right, so Arabic stays right to
  left. ESLint enforces it.
- **No hard-coded text**: every user-facing string is a key in `src/locales/{ar,fr,en}/*.json` with a
  real translation in all three languages.

## The non-negotiables

A pull request that breaks one of these rules will not be merged.

1. **Offline first.** Selling, returns, stock, cash closing, import and export, and printing work with
   no network at all. The DZBuild link is optional and never gates a feature.
2. **Tamper-evident books.** A validated sale, invoice or Z report is never edited or deleted:
   corrections go through a credit note or a return, numbering has no gaps, and the audit journal is a
   hash chain. Every write that touches stock or money runs in one SQLite transaction; stock is an
   append-only ledger.
3. **Forward-only migrations.** A schema change is a new numbered file in
   `crates/pos-core/migrations/`; existing migrations are never edited. The app backs up the database
   before it migrates.
4. **Three equal languages.** Arabic, French and English, on screen and on paper.
5. **Nothing illegal.** No fictive invoices, hidden or "non-billable" stock, sales deletion or any
   other tax-evasion feature (see the prohibited list in
   [`docs/01-MASTER-FEATURE-SPEC.md`](docs/01-MASTER-FEATURE-SPEC.md)).

## Pull requests

1. Fork the repository and create a branch from `main`: `fix/receipt-arabic-wrap`,
   `feat/scale-dibal`.
2. Keep one topic per pull request. Small pull requests are reviewed faster.
3. Write [Conventional Commits](https://www.conventionalcommits.org): `fix(printing): wrap long
   Arabic names`, `feat(stock): …`, `docs: …`.
4. **Sign off every commit** with `git commit -s`. It adds a `Signed-off-by:` line, which certifies
   the [Developer Certificate of Origin](https://developercertificate.org): you wrote the change or
   have the right to submit it under the project's licence.
5. Add or update tests. Run `pnpm check`.
6. Open the pull request and fill in the template. CI must be green; a maintainer reviews it.

By contributing you agree that your contribution is licensed under the
[GPL-3.0-or-later](LICENSE), like the rest of the code.

## Translations

Arabic, French and English strings live in `src/locales/{ar,fr,en}/<namespace>.json`; words printed on
receipts and invoices live in `crates/pos-docs/locales/{ar,fr,en}.json`.
[`src/locales/GLOSSARY.md`](src/locales/GLOSSARY.md) lists the business terms we use (kridi, versement,
droit de timbre…). Shop owners are not developers: keep wording short, plain and polite. A fix to one
word is a welcome pull request, or open a
[translation issue](https://github.com/DZBuild-com/dzbuild-pos/issues/new?template=translation.yml).

## Hardware reports

If you tested a printer, scanner, scale or display, send a
[hardware report](https://github.com/DZBuild-com/dzbuild-pos/issues/new?template=hardware_report.yml)
with the brand and model, the connection (USB, network, COM, Windows driver), the settings you used,
and what worked or did not. A photo of a printed receipt helps. Never include real customer data.

## How maintainers release

Releases are cut by the maintainers from `main`: `pnpm release:version` sets the version everywhere,
`pnpm release:changelog` drafts `CHANGELOG.md`, the release notes go in `src/release-notes/<version>.json`
in three languages, and pushing a `v*` tag runs the release workflow that builds the 64-bit and
32-bit setups. Signing keys stay in GitHub Actions secrets and never in the repository. The full
checklist is [`docs/release-checklist.md`](docs/release-checklist.md) and the steps are in
[`docs/release/RELEASING.md`](docs/release/RELEASING.md).
